# Paper and cyclic encoder comparison

## Purpose and implementation

Compare three implementations of the same exact curve-lifted code and the paper's
information set: paper transposed-Vandermonde solving plus additive evaluation;
cyclic polynomial encoding with Karatsuba; and cyclic encoding with a cached
FFT generator spectrum. See [implementation and API](../../encoding/liftrs/README.md#paper-and-cyclic-encoders),
[code](../../encoding/liftrs/orbit.go), [arithmetic](../../encoding/liftrs/orbit_arithmetic.go),
[transforms](../../encoding/liftrs/orbit_fft.go), [polynomials](../../encoding/liftrs/orbit_polynomial.go),
[artifact format](../../encoding/liftrs/orbit_artifact.go), and
[independent correctness checks](../../encoding/liftrs/orbit_test.go).
These are measured CPU experiments, not Monte Carlo capacity estimates or paper timings.

## Reproduction and evidence

- Run [run.py](run.py) from the repository root:
  `GOCACHE=/tmp/sk-depir-go-cache python3 experiments/encoder-comparison/run.py --go /tmp/sk-depir-go-toolchain/go/bin/go`.
  The `--go` path is optional; any compatible Go toolchain may be supplied.
- [main.go](main.go) is the exact driver. [results.json](results.json) records raw
  nanosecond timings, cumulative allocations, process peak RSS, source and artifact
  SHA256 hashes, timestamp, Go/Python versions, platform and base revision.
- [table.md](table.md) is generated from those results. All
  [public preprocessing artifacts](artifacts/) are generated by the script; filenames
  identify code and method, including the cached-FFT variant.
- Base revision `42e9180`, with this implementation initially uncommitted;
  results record exact source hashes so the base revision is not mistaken for the
  complete implementation. Environment: macOS 26.6.2 ARM64, Go 1.27.3, Python 3.9,
  18 logical CPUs reported by Python. The arithmetic is single-threaded; Go runtime
  GC uses its default configuration. Record the filesystem environment when comparing
  write/read results on other hosts.
- Requires Python 3 with POSIX `wait4`, a Go toolchain, writable temporary storage,
  and the repository's Go dependencies. No native compiler or GPU is required.

## Methodology and measurement boundaries

Each configuration uses m=2 and `(s,t)=(4,2),(5,3),(6,4),(7,6),(8,8)`.
Only the last is from the initial security catalogue; the others are comparison
fixtures. Discovery uses deterministic Go random seeds `1000+s` over the complete
good-monomial basis. These public reproducibility seeds are not PIR randomness.
The dimension K is exact, and discovery stops only when K support exponents are
found. The conservative default retry cap bounds failure, which returns an error.

**Preprocessing is entirely database-independent.** Time discovery separately,
then each method's preparation separately. FFT preparation includes cyclic generator
construction and its transform; it is a complete alternative, not incremental
setup to add to the Karatsuba preparation time. Serialization is separately recorded;
artifact file writes are excluded from preparation and encoding. Preparation is
one sample per method/code in fixed order; it is not a statistically robust setup
benchmark. The common discovery cost is charged once per distinct code, not once
per method or database.

Serialize all public artifacts. Run each encoding method in a fresh process,
reading and loading its complete artifact once; no degree discovery, polynomial
preparation or fixed-generator transform is repeated per database. Record artifact
read time and load time separately. Loading rebuilds runtime field/FFT tables;
serialized paper reciprocals/weights and cyclic polynomials/spectra are reused.
The loaded encoder exposes its immutable basis metadata for dimension and index
checks; no second copy of runtime field/transform tables is created by the driver.

Supply a uniform deterministic message (seed 71), then perform three encoding calls
with the same loaded encoder/message. Timings include message-dependent allocation,
arithmetic, coordinate ordering and base-field checks, but exclude message generation,
artifact loading, output hashing and file I/O. Report the median; the raw three values
and cumulative Go allocation bytes are retained. There are no interleaved method runs,
confidence intervals or performance regression thresholds.

Compare SHA256 of complete canonical-grid outputs for all three methods; validate
every message value at its systematic position. Unit tests additionally check all
message basis vectors against the existing dense oracle on eight tiny codes. That
oracle uses a different information set; tests reconstruct from the new word's values
at its pivot positions rather than comparing encodings of differently interpreted
messages. Separate tests validate the cached-FFT artifact and concurrent reuse.

Measure process peak RSS with `wait4` for each child, including loading, repeated
encoding, validation and output I/O. Darwin reports bytes; Linux reports KiB,
converted to bytes. This avoids counting the Go compiler's memory. Cumulative
allocation is not live heap or peak memory. An initial `/usr/bin/time -l` attempt
could not read `kern.clockrate` in the sandbox; `wait4` replaced that measurement
before the committed results were generated.

After timing encoding, serialize one word to an explicit little-endian uint32
buffer, write/sync/close a temporary file, then read it back and check its hash.
Report sync-write and cached-readback times separately. The sink stores `4*N` bytes,
not the bit-packed protocol format; small-file timings do not measure sustained disk
throughput. Intermediate polynomial I/O and artifact-generation I/O are not measured.
No permutation, masking, application partitioning or storage-group assembly is timed.

## Interpretation and limits

See [table.md](table.md). All five configurations produce identical outputs across
the three methods. Full prepared artifacts remain below 1 MiB each in this grid,
so distributing these particular artifacts in GitHub is practical. This does not
establish artifact size or feasibility for s=9..20; their arrays grow with code size.

At N=65,536, the initial measured comparison favors the cached-FFT cyclic variant
over both Karatsuba cyclic encoding and the paper implementation, while its one-time
preparation is substantially more expensive. The speed and space tradeoff therefore
depends on reuse. Three local samples do not establish a general winner. The paper
solver, product-tree scheduling, polynomial multiplication and field kernels are
not fully optimized. FFT cyclic multiplication uses extension-field arithmetic,
so these results do not demonstrate a base-field-only quasi-linear multiplier.

The backend is bounded to N<=65,536, in memory, with no GPU or external-storage
implementation. Preparing/loading trusted public artifacts is separate from handling
untrusted databases: structural loader validation does not certify that a supplied
artifact describes the intended code. Publish source/provenance and independently
verify artifacts. This experiment does not establish deployment security, target-size
feasibility or a production API.

## Subsequent documentation and catalogue corrections

PLAN-014 narrows the `PrepareCyclicFFT` complexity comment: only the G*H product
uses the full FFT; H=(P*M) mod X^K still uses Karatsuba. No arithmetic or measured
result changed. The saved orbit.go hash therefore identifies the measured source
at revision `0a4bb38`, not that later comment-only edit. Current catalogue evidence
now records exact K=3121 for s=8,m=2,t=8, preserving Monte Carlo evidence separately.
Standalone support does not imply integration with application plans or grouped
storage. Per-stage memory and packed/grouped output measurement remain future
acceptance checks; the reported process RSS and uint32 sink are not those measurements.
